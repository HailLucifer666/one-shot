## ARCHITECTURE SUMMARY

The skill is prose, not code: its "runtime" is a probabilistic executor (the model), and its
failure mode is an instruction a compliant-but-lazy agent can skip without anything downstream
noticing. The defense architecture is artifacts: every section mints a file (SPEC/STACK/PLAN/
PROGRESS/ASSUMPTIONS/BLOCKERS, one-shot-work/ itself, GATE.md), so post-hoc checks (the benchmark
fingerprint, the scoring pre-pass) can verify a run happened and how. The benchmark is a two-arm
design with sentinel-gated result records and a scorer that deliberately fails open to MANUAL
rather than guess. The weakest joint in the whole chain is consistent: **instructions whose
compliance leaves no artifact** — the gate's ticks, the self-review's findings, the on-disk
verification listing — where the only evidence is prose the same agent wrote.

## KEY DEPENDENCIES

- **The host harness** (ZCode/OpenCode/…): picks which skill fires, supplies the session, and
  records `run-complete.json` sentinels. If the harness misfires, the skill never runs (the Mercury
  3 incident). The skill cannot defend its own selection; it can only make the substitution
  detectable afterwards (one-shot-work/ fingerprint).
- **The Respan gateway** (`run_benchmark.py run`): dead without `RESPAN_API_KEY` (absent from the
  tree — verified). `init`/`summary` work without it.
- **The model's honesty** for every self-report-only rule: contrast ratios, version checks, audit
  runs, clean checkout, on-disk listings. No tool checks any of these today.
- **`_runs-zcode/` staying put**: the published README numbers point at it; it is outside the repo
  and would not survive a clone.

  limiting, dependency audits. No dangerous advice found in any skill file.

## The constraints that produced what follows

Nothing here was a bad decision at the time. Three constraints compounded. First, one weekend,
solo: the skill was iterated incident-by-incident (three real external failures, each fixed within
hours), which optimizes for the failures you've seen and leaves the letter behind the practice —
the artifacts show better behavior than the instructions require. Second, the enforcement tooling
grew where the work was (a throwaway scoring pre-pass, smoke validators), so the repo's committed
tools enforce less than the protocol the README describes. Third, three skill versions landed in
four days and the doc layer (README, docs/) was written at v0.1 and not relabelled — the version
story is the repo's biggest honesty gap, and it is entirely presentational.

### BACKLOG (real, sequenced; not for today)

- **B1 — The PRD path leaves SPEC.md empty and the gate vacuous (highest-value gap).**
  SKILL.md:26 writes SPEC.md content only on "No PRD"; SKILL.md:16 creates the template on every
  run; gate.md:6 checks "every acceptance criterion in SPEC.md". With a user-supplied PRD — the
  skill's own headline trigger — a letter-compliant agent leaves SPEC.md as bare headings and the
  gate passes over zero criteria. Benchmark practice exceeded the letter (all skill-arm SPEC.md
  files are filled), but the skill's stated purpose is helping weak models — the population least
  likely to do unfilled-instruction work. *Fix: "With a PRD: extract its acceptance criteria into
  SPEC.md before planning; the gate checks SPEC.md, not the PRD."*
- **B2 — Reset-survivable state doesn't record identity, rigor, or the gate obligation.**
  PROGRESS.md's template has a blank `Rigor level:` field nothing orders filled, no skill
  identity, no gate status. After a context reset (the Mercury-3 environment), the agent that
  re-reads PROGRESS.md as instructed finds no trace that a gate is owed. *Fix: template header
  "Skill: one-shot | Rigor: <level> | Gate: not run", fill at setup; §9 step 1: confirm
  one-shot-work/GATE.md exists.*
- **B3 — The evidence family: verification claims leave no verifiable trace.** On-disk listing
  (SKILL.md:41,73) can be written from the plan; self-review findings and contrast ratios have no
  mandated destination (SKILL.md:46); GATE.md stores ticks, not command output. A fabricated tick
  is indistinguishable from a real one after the fact. The smoke run did all three voluntarily —
  the letter should require what practice already does. *Fix (v0.1.3 candidate): paste listing
  output into PROGRESS.md; review findings + computed ratios into PROGRESS.md or GATE.md; one
  evidence line per gate tick.*
- **B4 — The gate cannot fail (DECISION needed).** gate.md:3/6 and SKILL.md:54 let *any* unmet
  acceptance criterion convert to "known limitation" and the run still reports done. There is no
  threshold at which the run's own gate says FAILED. Deliberate honesty-mechanism or missing
  blocking state — that is a product decision, not a wording fix. Proposed resolution: criteria
  unmet ⇒ run is not done; Known limitations only for gaps that are not acceptance criteria.
- **B5 — No testing minimum outside app.md (DECISION needed).** web.md and the no-module path
  (slides/games/documents) mandate zero tests, so gate.md:7 "All tests pass" is vacuously true at
  zero, and SKILL.md:37 "when practical" is a self-granted exemption. What is the minimum bar for
  a static deliverable — one automated check of the primary action? Decide, then word it.
- **B6 — STACK.md is filled only on the no-stack path.** SKILL.md:27 is conditional; stack.md:38's
  content requirement lives inside the choosing module; SKILL.md:28's version check has no
  destination, so "verified (date)" can be typed without running anything. *Fix: STACK.md always
  filled (user-mandated rows marked as such); paste the verify command output.*
- **B7 — Both escalation paths dead-end with no user.** "Ask ONE batched message, then continue"
  (SKILL.md:22) and the retry cap's "then ask the user" (SKILL.md:43) have no defined outcome when
  no answer can arrive mid-run, and neither logs the unresolved item. *Fix: record in BLOCKERS.md
  with the chosen safe default; surface open blockers in the final report.*
- **B8 — ASSUMPTIONS.md is write-only.** web.md:26 mandates sample-content disclosure into it, but
  no gate item or report line ever reads it back — invented testimonials can ship unseen. *Fix:
  gate Delivery item "ASSUMPTIONS.md reviewed"; report lists material assumptions.*
- **B9 — `run_benchmark.py summary` does not enforce the sentinel protocol.** Probed 2026-11-01:
  a scored RESULT.json with no `run-complete.json` anywhere is summarized (`summary()`, lines
  104–126, skips only null scores). The gating lived in the throwaway pre-pass. *Fix: require
  `run-complete.json` with `exit: "completed"` in summary(); the probe dir
  `_probe/sentinel-test/` is the failing test — it must disappear from the table after the fix.*
- **B10 — checks.py spec04 HTML branch silently drops three criteria.** For HTML decks, criteria
  6/8/10 print only when note-markers land in 1–7; at 0 or ≥8 they are never printed (the
  `manual_block` at checks.py:408–412 is nested inside the `else`). Verified live: all four 04
  runs' outputs lack c6/c8/c10 lines, while the drafts recorded them MANUAL — the published 10/10
  does not rest on the gap, but anyone re-scoring per SCORING.md gets 7 lines where 10 are
  promised ("Prints one line per criterion", checks.py:6). *Fix: dedent the manual_block; add a
  mutation probe.*
- **B11 — HTML notes PASS checks presence, not content.** checks.py:398–400 passes c4 on ≥8
  note markers with no content check (the pptx branch checks content at :326–330). All three HTML
  decks in the tree have real static notes content, so no published result is affected. *Fix:
  require non-empty marker text, fail-open to MANUAL otherwise.*
- **B12 — Reproducibility: the evidence travels with neither repo nor README.** 40 placeholder
  RESULT.json in `benchmark/runs/`; real records in `_runs-zcode/` (outside); pre-pass throwaway.
  *Fix at publish: vendor the 20 RESULT.json + draft.json + run-complete.json into
  `benchmark/runs/` (or a released artifact), and say in README what wrote them.*
